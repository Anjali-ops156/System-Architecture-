The problem

Small salons still run on a phone and a paper register. That costs the owner money in five specific ways — and each one is answered by a feature in this design.

What goes wrong today

  • Calls missed during the evening rush
  • Two customers promised the same stylist at 5 PM
  • 20–30% no-shows, because no reminder is sent
  • Paper bills, so no customer history
  • No reports — the owner cannot see what earns

What the system does

  • Customers book a verified slot with a chosen stylist
  • The database makes a double-booking impossible
  • Automatic confirmation and 24-hour reminder emails
  • Staff bill at the chair; invoices are permanent
  • One dashboard for revenue and utilisation

Documents

Four documents, each covering a different layer of the design. Start with the diagrams if you want the shape of the system in two minutes.

The one idea worth reading first

Two customers can open the booking page at the same moment, both see 5 PM as free, and both tap Confirm in the same second. Preventing that is the hardest problem in this system, and it is solved in two independent layers:

Layer 1 — application lock

The server never trusts the browser’s slot list. It opens a transaction, takes a row lock on that stylist’s day, and re-checks. The loser gets 409 Conflict and is returned to the time picker with fresh data. This gives a good error message.

Layer 2 — database constraint

A PostgreSQL GiST exclusion constraint makes two overlapping bookings for one stylist physically impossible — even by direct SQL, even if the application code above it has a bug. This gives a guarantee.

Why this makes a defensible project

It contains one genuinely non-trivial algorithm — computing real availability and preventing a double-booking under concurrent requests — rather than being a set of CRUD forms. That single problem is what carries a viva.

Around it sits everything a systems course wants to see: clean three-tier separation, a normalised relational schema with snapshot integrity, three server-enforced permission sets, an external payment integration, and a full deployment on free infrastructure.

Viva point — where security actually lives

Hiding a button in React is user experience, not security: anyone can call the API directly with a saved token. Every protected route therefore passes through an authorize(role) middleware on the server, and that middleware — not the absent button — is the security boundary.

The test that proves it: call an admin endpoint with a customer’s token. It must return 403, not data.

Core business logic

1 · Slot generation

INPUT  staffId, date, serviceIds

 1  total_duration = Σ duration of the selected services
 2  salon working hours for that weekday    → if closed, return []
 3  date in the holiday list                → if yes,    return []
 4  that staff member's shift for that weekday → if weekly off, return []
 5  window = intersection(salon hours, staff shift)
 6  approved leave covering the date        → if full day, return []
 7  candidates = window.start … (window.end − total_duration)
                 stepping by settings.slot_interval        e.g. 30 min
 8  busy = existing bookings for (staffId, date)
           with status IN (pending, confirmed, in_progress)
         + blocked_slots
 9  reject any candidate that OVERLAPS a busy interval:
        overlap ⟺ newStart < busyEnd AND newEnd > busyStart
10  if date = today, also reject candidates already in the past

RETURN the remaining candidates

2 · Double-booking prevention

The slot list the browser is holding can go stale. Two customers can tap 5:00 PM in the same second. So the check is repeated on the server, authoritatively:

  • POST /api/bookings opens a database transaction
  • It re-runs the overlap check with a row lock — SELECT … FOR UPDATE — on that stylist’s bookings for that date
  • It inserts only if the slot is still free; otherwise it returns 409 Conflict with “that slot was just taken — please pick another”

On top of that, PostgreSQL enforces the same rule at the schema level, so a clash is physically impossible even if the application code has a bug:

EXCLUDE USING gist (
    staff_id WITH =,
    tsrange(booking_date + start_time, booking_date + end_time) WITH &&
) WHERE (status IN ('pending','confirmed','in_progress'))
Viva point — the strongest demo in the project

Fire two simultaneous booking requests at the same stylist, date and time. Exactly one returns 201; the other returns 409. Then try to insert the clash directly in SQL — the exclusion constraint rejects it too.

This demonstrates the thing most student projects miss: correctness is not just validation on the form, it is defence at every layer that can be reached independently.

3 · Booking status state machine

  pending ──(advance paid)──► confirmed ──► in_progress ──► completed
     │                            │
     └────────► cancelled ◄───────┘
                                  └──(grace period elapsed)──► no_show

  Terminal states: completed · cancelled · no_show
  Any transition not drawn above is rejected with 400.

4 · Bill calculation — a fixed, documented order

subtotal         = Σ (unit_price × quantity)
coupon_discount  = flat value, OR (subtotal × percent) capped at max_discount
                   requires subtotal ≥ min_bill_amount
loyalty_discount = points_used × rupee_value_per_point, capped at the remainder
taxable          = subtotal − coupon_discount − loyalty_discount
tax_amount       = taxable × gst_percent
total_amount     = taxable + tax_amount
balance_due      = total_amount − advance_paid

A worked example to check the implementation against: subtotal ₹1,000, a 10% coupon capped at ₹80, 50 points at ₹1 each, GST 18%, advance ₹200 → taxable ₹870, tax ₹156.60, total ₹1,026.60, balance ₹826.60.

5 · Loyalty points — an append-only ledger

Points are awarded only when a bill is finalised: floor(taxable / amount_per_point_earned) × points_per_amount. Every credit and debit is a row in loyalty_ledger, and the balance is SUM(points).

Viva point — why a ledger, not a balance column

A single points_balance column drifts out of sync the first time an operation fails halfway through. A ledger cannot drift, and it gives the customer a history they can audit — the same reason real accounting systems never store only a balance.

Section 3

Architecture style & principles

The style is a layered modular monolith with a decoupled single-page client — one deployable API, internally separated into strict layers. This is a deliberate choice over microservices, recorded as ADR-001.

P1 · One source of truth per rule

A business rule is implemented once, in the service layer. Slot availability is decided in SlotService and nowhere else, so the customer wizard, the staff walk-in screen and the admin calendar cannot disagree.

P2 · Never trust the client

The browser is a rendering surface, not an authority. Roles, prices, discounts, slot availability and payment status are all decided server-side, regardless of what the request claims.

P3 · Defend correctness in depth

Where a rule protects money or a promise to a customer, it is enforced at more than one layer — application and database — so a single bug cannot breach it.

P4 · History is immutable

Invoices, payments and the loyalty ledger are append-only. Records are superseded, deactivated or reversed — never edited or deleted in place.

P5 · Stateless API

No session state in process memory. Any instance can serve any request, which is what makes the horizontal scaling path in §14 a configuration change rather than a rewrite.

P6 · Boring where it does not matter

Complexity is spent on the slot engine and the billing transaction. Everything else uses the most conventional approach available, because unremarkable code is what leaves time for the hard part.

Critical flows

Three flows carry the architectural weight of the system. Each is shown as a sequence diagram with its transaction boundary marked, because in all three cases the boundary is the design.

8.1 · Concurrent booking — the correctness flow

sequenceDiagram
  autonumber

  participant B as Customer B
  participant API as BookingService
  participant DB as PostgreSQL

  Note over A,B: Both are viewing the same slot list, fetched seconds ago
  A->>API: POST /bookings — 5:00 PM, Stylist R
  B->>API: POST /bookings — 5:00 PM, Stylist R

  Note over API,DB: Request A — transaction opens
  API->>DB: BEGIN
  API->>DB: SELECT bookings FOR UPDATE where staff_id=R and date=today
  DB-->>API: rows locked, 5:00 PM is free
  API->>DB: INSERT booking A
  DB-->>API: accepted, exclusion constraint satisfied
  API->>DB: COMMIT
  API-->>A: 201 Created — booking confirmed

  Note over API,DB: Request B — was blocked on the lock, now proceeds
  API->>DB: BEGIN
  API->>DB: SELECT bookings FOR UPDATE where staff_id=R and date=today
  DB-->>API: lock acquired, 5:00 PM now taken
  API->>DB: ROLLBACK
  API-->>B: 409 Conflict — slot just taken, choose another

  Note over B: UI returns to Step 3 with a freshly fetched slot list

Figure 5 — Concurrent booking sequence. Request B is not rejected by validation — it is rejected by the lock. The row lock serialises the two requests, so the second one reads a world in which the first has already committed. Even if this application code were removed entirely, the exclusion constraint at step 6 would still refuse the duplicate insert.

Why two layers for one rule

The application lock gives a good error message; the database constraint gives a guarantee. The lock can be defeated by a future code path that forgets to open a transaction. The constraint cannot be defeated by any code path at all, including a manual SQL fix at 2 AM. Principle P3 in practice.

8.3 · Bill finalisation — the atomicity flow

sequenceDiagram

  CS-->>API: discount allowed, or reason refused
  API->>LS: value the points being redeemed
  LS->>DB: SUM ledger to confirm the balance covers it
  LS-->>API: loyalty discount
  API->>API: taxable, then GST, then total, then balance due
  API->>DB: UPDATE bill — totals, status finalized
  API->>DB: INSERT coupon_usage and increment used_count
  API->>DB: INSERT ledger row — negative, points redeemed
  API->>DB: INSERT ledger row — positive, points earned on taxable
  API->>DB: assign invoice_number from sequence
  API->>DB: COMMIT

  API->>ES: send invoice email, then review request
  API-->>S: 200 — invoice INV-2026-0001, bill locked

Figure 7 — Bill finalisation sequence. Six writes in one transaction. If the ledger insert failed after used_count had been incremented, a customer would lose a coupon and gain nothing — so the boundary wraps all of it. Note that the email is sent after commit, deliberately: a mail provider timeout must never roll back a completed sale.

The rule this flow encodes

Anything that must agree goes inside one transaction. Anything that can be retried later goes outside it. Money, discounts and points must agree, so they are atomic. An email can be resent from the email log, so it is not.

Section 12

Observability

Logging

Structured JSON to stdout, collected by the platform. Every line carries the request id, route, role, latency and outcome. Four levels, used honestly: error means someone must look, warn means a rule refused something, info for lifecycle, debug off in production.

Metrics that matter

Slot-query p95, booking-write p95, 409 rate — a rising 409 rate means the slot list is going stale too often — webhook failure count, email failure count, and cold-start frequency.

Health & readiness

GET /health is shallow and public, for the uptime ping. GET /ready checks the database round-trip and is used by CI after a deploy to decide whether the release is good.

Business-visible failure

Two failures are invisible in logs but obvious to a user, so each has a screen: /admin/notifications lists every email with its status and a resend action, and /admin/payments exposes pending and failed transactions for reconciliation.

Error tracking

Sentry on both tiers, free tier. Unhandled exceptions and unhandled promise rejections are captured with the request id, so a user-reported problem can be traced to a single log trail.

Audit trail

Distinct from logs and permanent. Logs answer "why was it slow"; the audit table answers "who changed this price, and what was it before".

Section 15

Architecture decision records

Eight decisions that shaped this design, each with the alternatives that were rejected and the cost of the choice. The negative consequences are stated because a decision record that lists only benefits is marketing, not engineering.

ADR-001Layered modular monolith, not microservicesaccepted
Context
The system has clear domains — scheduling, billing, loyalty, notifications — which invites splitting them into services.
Decision
One deployable API, internally split into strict layers with service-level module boundaries.
Alternatives
Microservices per domain — rejected: distributed transactions would be required for the billing flow in Figure 7, which is currently a single atomic block. Serverless functions — rejected: cold starts and connection-pool pressure hurt exactly the flow that must be fast.
Consequences
Positive: one repo, one deploy, one log stream, real transactions. Negative: the whole API scales as one unit, and module boundaries are enforced only by discipline and code review, not by the network.
ADR-002PostgreSQL, not a document databaseaccepted
Context
The data is highly relational: bookings reference staff, services, bills, payments, coupons and reviews, and reports aggregate across all of them.
Decision
PostgreSQL 16, with integrity enforced by the schema.
Alternatives
MongoDB — rejected: every report becomes a hand-written join, and there is no equivalent of the exclusion constraint that makes ADR-003 possible.
Consequences
Positive: foreign keys, CHECK and UNIQUE constraints, real transactions, SQL aggregation for reports. Negative: schema changes require migrations, so early iteration is slightly slower.
ADR-003Booking exclusivity enforced by the database, not only the applicationaccepted
Context
A double-booking is the single worst correctness failure in the domain. Application-level checking is vulnerable to any future code path that forgets to take a lock.
Decision
A GiST exclusion constraint on (staff_id, time range) for active statuses, in addition to a transactional row-lock check.
Alternatives
Application check only — rejected: one missed transaction reintroduces the bug. Unique index on a discrete slot column — rejected: cannot express overlap for variable-duration services.
Consequences
Positive: the invariant holds against application bugs, concurrent requests and manual SQL alike. Negative: ties the design to PostgreSQL, and the constraint violation must be translated into a friendly 409 rather than surfacing as a raw database error.
ADR-004JWT access token plus rotating refresh tokenaccepted
Context
The SPA and API are on different origins, and the API must stay stateless for the scaling path in §14.
Decision
A short 15-minute access token, with a 7-day refresh token in an httpOnly cookie, stored hashed and revocable.
Alternatives
Server-side sessions — rejected: introduces shared state and breaks P5. Long-lived access token alone — rejected: cannot be revoked and stays valid long after logout.
Consequences
Positive: any instance can serve any request; logout genuinely revokes. Negative: a refresh endpoint and silent-renewal logic on the client is real added complexity, and an access token remains valid for up to 15 minutes after a role change.
ADR-005Append-only loyalty ledger, not a balance columnaccepted
Context
Points are earned, redeemed, expired, adjusted by an admin and reversed on refund. A single mutable balance must be correct after every one of those paths.
Decision
Every movement is a signed row in loyalty_ledger; the balance is SUM(points).
Alternatives
users.points_balance incremented in place — rejected: drifts permanently the first time an operation fails halfway, with no way to reconstruct the truth.
Consequences
Positive: cannot drift, fully auditable, and the customer gets a history for free. Negative: reading a balance is an aggregate rather than a column read, which needs an index and eventually a periodic snapshot row.
ADR-006Gateway webhook is the sole source of payment truthaccepted
Context
After checkout the browser reports success, but the browser is under the user's control and can be replayed or forged.
Decision
Only a signature-verified webhook transitions a booking to confirmed. The browser's verify call renders an optimistic success screen and nothing more.
Alternatives
Trusting the client callback — rejected: trivially forgeable, would allow free bookings. Polling the gateway — rejected: wasteful and slow, though retained as a reconciliation fallback for stuck payments.
Consequences
Positive: payment status cannot be forged; replays are idempotent. Negative: a publicly reachable endpoint that must be carefully signature-checked, and local development needs a tunnel to receive webhooks.
ADR-007Price snapshots on booking lines, not live joinsaccepted
Context
Service prices change. An invoice must remain reproducible years later for the retention requirement in NFR-12.
Decision
booking_services stores service_name_snapshot, price_snapshot and duration_snapshot at the moment of booking.
Alternatives
Join live to services — rejected: silently rewrites every historical invoice whenever a price changes. Full price-history table with validity ranges — rejected: correct but heavier than this scale justifies.
Consequences
Positive: invoices are immutable and reproducible. Negative: looks like denormalisation to a reader who does not know why, which is precisely why it is recorded here.
ADR-008In-process cron now, external queue lateraccepted
Context
Reminders, the no-show sweep and point expiry are time-triggered. The free hosting tier offers no managed scheduler and sleeps when idle.
Decision
node-cron inside the API process, woken by an external HTTP ping against a secret-protected endpoint.
Alternatives
A separate worker service — rejected: doubles the hosting footprint for a few minutes of daily work. A managed queue — rejected for now: correct at Stage 3, unjustified at Stage 1.
Consequences
Positive: no extra infrastructure, and the ping doubles as the keep-awake mitigation for the cold start. Negative: a job cannot run while the container sleeps, and with multiple instances jobs would run more than once — which is exactly the trigger to move to a queue.

How to explain your project

Simple English you can actually say out loud. Read the green boxes word for word, or in your own words once you are comfortable.

Before anything else

The three things that matter most

If you remember nothing else from this page, remember these. Almost every good mark comes from these three ideas.

Say these three things clearly and you have done well

  1. The problem is real and specific. Salons lose money in five exact ways. Do not say "to make work easier" — say the five losses. A specific problem shows you studied the business, not just the technology.
  2. Double-booking is stopped in two independent layers. The application lock gives a good error message. The database constraint gives a guarantee. Code can have bugs; the constraint cannot be bypassed. This is the strongest point in your whole project.
  3. Nothing is decided in the browser. Roles, prices, discounts, slot availability, payment status — all decided on the server. Hiding a button is not security.
One habit that helps a lot

When you explain something, always say why after what. "I used PostgreSQL" is a fact. "I used PostgreSQL because my data is highly relational and it gives me the constraint that prevents double-booking" is an answer. Sir is testing whether you understand your own choices.

Part 1

The 60-second version

Use this when sir says "tell me about your project" and you have very little time — or as your opening before the full explanation.

Say this

Good morning sir. My project is called SalonEase. It is an appointment booking and management system for a local salon.

Right now small salons take all bookings on the phone. So calls get missed during rush hours, two customers sometimes get the same stylist at the same time, and about twenty to thirty percent of customers do not turn up because there is no reminder. Billing is on paper, so the owner has no record and no reports.

My system solves this. The customer books a confirmed slot with a chosen stylist online. The staff runs the day from a live schedule and makes the bill at the chair. The owner sees revenue and performance on one dashboard.

I have used a three-tier architecture — React for the frontend, Node.js with Express for the backend, and PostgreSQL for the database. There are three user roles: Customer, Staff and Admin. The whole project runs on free hosting, so the running cost is zero.

Sir, the most difficult part was making sure two customers can never book the same stylist at the same time. I can explain that in detail if you want.

↑ End here and stop. That last line invites sir to ask about your best work.
Part 2

The full explanation — about 7 minutes

Seven steps in order. Each has the words to say, and what to point at on screen.

STEP 1Start with the problem ~60 sec
Say this

Sir, before I show the system, I want to explain the problem. I studied how small salons in our area work. They take all bookings on a phone and write them in a paper register. This causes five real losses for the owner.

First — during evening rush hours, calls get missed. That customer books somewhere else.

Second — there is no single record of who is free at what time. So sometimes two customers are promised the same stylist at 5 PM, and one has to be turned away.

Third — there is no confirmation or reminder. So around twenty to thirty percent of customers do not come. That stylist's chair earns nothing for that full hour.

Fourth — billing is on loose paper slips. So the owner has no record of what a customer spent or what service they preferred.

Fifth — there are no reports at all. The owner cannot tell which service or which stylist actually earns the most money.

Why start here

Most students start with "I used React and Node". Starting with five specific business losses immediately shows you solved a real problem. It also sets up every feature you show later — each one answers one of these five.

STEP 2The three user roles ~45 sec
Say this

Sir, my system has three types of users.

The Customer can browse services, book an appointment for himself, pay an advance, see his own bookings and give a review after the service.

The Staff member — that is the stylist — sees only his own day's schedule. He can start and complete an appointment, create a booking for a walk-in customer, and make the bill.

The Admin is the salon owner. He can do everything — add and edit services and prices, create staff accounts, set their working shifts, approve leave, create discount coupons, and see all the reports and revenue.

Sir, one important point here. I check the role on the server, not in the browser. Hiding a button in React is only for the user's convenience — it is not security. Anyone can call my API directly with a saved token. So every protected route passes through a middleware on the backend that checks the role before the request reaches any business logic.

Point at

The permission table in the functional spec document — the one with ticks and crosses for the three roles.

STEP 3The architecture diagram ~90 sec
Open now

Figure 1 — the coloured architecture diagram. Keep it on screen for this whole step.

Say this

Sir, this is my system architecture. I have used a three-tier architecture. Each colour is one layer.

At the top, in purple, are the users — Customer, Staff and Admin. They all use a normal web browser.

The blue layer is my frontend. This is React. It has thirty-nine screens grouped by role. Sir, this layer only shows things — it does not decide anything. It sends the request and displays whatever the backend replies.

The green layer is my backend. This is Node.js with Express. All my business logic lives here. At the top of this layer is the middleware — it checks CORS, then the JWT token, then the role, then validates the input. Only after all four checks does the request reach my controllers. Below that is the service layer, which holds all the actual rules. And at the bottom is the repository layer — the only layer that is allowed to write SQL.

The orange layer is my database, PostgreSQL, with twenty-five tables.

On the right in red are the external services — Razorpay for payment, Resend for email, Cloudinary for images.

Sir, the most important thing in this diagram is what is not there. There is no arrow from the browser to the database. The browser can never reach the database directly. It must pass through the API, where all the security checks happen.

If sir asks why you separated the layers

"Sir, so that one business rule exists in only one place. My slot availability logic is written once in SlotService. The customer booking page, the staff walk-in page and the admin calendar all call that same code. So they can never disagree with each other. If I had written the logic in three places, one day they would go out of sync."

STEP 4The hard part — the slot problem ~2 min · most important
Open now

Figure 2 — the booking flow diagram with the green 201 and red 409 split.

Say this — slowly, this is your best part

Sir, now I want to explain the most difficult part of my project.

When a customer opens the booking page, I have to show him only the genuinely free times. To find those, I check four different things. First, the salon's working hours for that day. Second, that particular stylist's shift, because every stylist has different timings and a weekly off. Third, whether he has approved leave on that date. And fourth, his existing bookings for that day.

Then I check for overlap. Because a service has a duration — a haircut is thirty minutes but a bridal package may be two hours. So I cannot just check if the start time is free. I check whether the new appointment's full time range overlaps any existing one.

But sir, there is a bigger problem here.

↑ Pause here. Let sir think for two seconds. Then continue.

Suppose two customers open the booking page at the same time. Both see 5 PM as free, because both lists were fetched a few seconds ago. Now both click Confirm in the same second. What will happen? Both requests come to my server, both think the slot is free, and my stylist gets double-booked.

So sir, I solved this in two independent layers.

First layer. When the booking request reaches my server, I do not trust the browser's list at all. I open a database transaction, I take a row lock on that stylist's bookings for that date, and I check the slot again on the server. If it is still free, I insert and commit. If someone else has already taken it, I roll back and return 409 Conflict — and the frontend sends that customer back to the time selection step with a freshly loaded list. The lock forces the two requests to happen one after the other instead of together.

Second layer. Sir, I also added a constraint inside the database itself. It is called an exclusion constraint. It tells PostgreSQL that one stylist can never have two overlapping active appointments. So it is physically impossible to insert a clashing booking — even by direct SQL, and even if my application code has a bug tomorrow.

Sir, the reason I did both is this. The application lock gives the customer a good error message. The database constraint gives a guarantee. My code can have a bug. The constraint cannot be bypassed by any code at all.

This is the moment to demo, if you can

Open two browser windows, both on the same 5 PM slot, and click Confirm in both. One shows success, the other shows the 409 message. Then say: "Sir, and if I try to insert that clashing row directly in SQL, the database also refuses it."

If sir asks only one deep question in the whole viva, it will most likely be about this. Practise this step more than any other.

STEP 5The database ~90 sec
Open now

Figure 3 — the relationship map with bookings in the centre.

Say this

Sir, I have twenty-five tables. But I built them in two phases. Fourteen core tables make the whole system work end to end, and the other eleven add the extra features like coupons, loyalty points and the audit log. I did this so that at every stage I had something working to show, instead of a half-finished system at the end.

Sir, as you can see, the bookings table is at the centre. Almost everything connects to it. One booking has exactly one bill, but one bill can have several payments — an advance first, then the balance, and maybe a refund. One booking can include several services, and one service appears in many bookings, so that is a many-to-many relationship and I used a junction table called booking_services.

Sir, I want to explain one design decision in that junction table. I do not only store the service ID. I also store a copy of the price at the time of booking.

Sir, the reason is this. Suppose today a haircut is three hundred rupees. Next month the owner increases it to four hundred. If my invoice joins to the live services table, then my old bill from last month will also start showing four hundred rupees. That is wrong — a past invoice must never change. Also we have to keep invoices for seven years for tax. So I store a snapshot of the price, the name and the duration at the moment of booking.

Sir, it looks like duplicate data, but it is actually about correctness, not about saving a join.

STEP 6Payment and security ~60 sec
Say this

Sir, for online payment I used Razorpay in test mode. No real money and no business account is needed — only test cards.

Sir, one important point about payment. After the customer pays, his browser tells my server that the payment was successful. But I do not believe the browser, because the browser is in the user's control and that message can be faked. Someone could get a free booking.

So I only confirm a booking when Razorpay itself sends a signed webhook directly to my server. I verify the signature using my secret key. That webhook is my only source of truth for payment. The browser's message is only used to show the success screen quickly so the customer does not have to wait.

For the rest of the security, sir — I hash passwords with bcrypt at twelve rounds and I never return the hash in any API response. For login I use a JWT access token that expires in fifteen minutes, with a refresh token in an httpOnly cookie so JavaScript cannot read it. All my SQL is parameterised, so SQL injection is not possible. And I validate every input with a Zod schema before it reaches any logic.

Sir, I also never store card numbers or UPI details anywhere. The card is entered inside Razorpay's own page. I only receive a payment ID back.

STEP 7Hosting, then close ~45 sec
Say this

Sir, the whole project is deployed on free hosting. The frontend is on Vercel, the backend on Render, and the database on Neon, which is managed PostgreSQL. Images go to Cloudinary and emails through Resend. The total running cost is zero rupees per month, and no credit card is needed anywhere.

Sir, I should also mention one honest limitation. The free backend goes to sleep after fifteen minutes of no use, so the very first request after that takes about fifty seconds. I keep it awake with a free cron service that pings a health endpoint every ten minutes. I have documented this as a known trade-off of using free hosting.

Sir, that is my architecture. Shall I show you the working demo?

Why admit the limitation yourself

Because sir may notice the slow first load anyway. If you mention it before he asks, it looks like engineering awareness. If he catches it first, it looks like a bug you did not know about. Same fact, completely different impression.

Part 3

Questions sir will probably ask

Fourteen likely questions with short, confident answers. Read the answer once, then say it in your own words — it will sound more natural than memorising.

Q1Why did you use PostgreSQL and not MongoDB?

Sir, my data is highly relational. One booking connects to the customer, the stylist, the services, the bill, the payments, the coupon and the review. And all my reports need joins across these tables.

In MongoDB I would have to do those joins manually in my code, which is more work and slower. Also, PostgreSQL gives me the exclusion constraint which is what actually prevents my double-booking. MongoDB has no equivalent feature. So for this project a relational database was clearly the right choice.

Q2Why not microservices? It is more modern.

Sir, my bill finalisation writes to six tables and all six must succeed together — the bill, the coupon usage, the coupon counter, two ledger rows and the invoice number. In one database I can do that in a single transaction, so either all of it happens or none of it happens.

If I split into microservices, I would need distributed transactions, which are much harder to get right. Also I am one developer, so microservices would give me much more deployment and monitoring work with no real benefit at this scale.

But sir, I kept my code in clean layers with separate services. So if this grows to many salons later, the boundaries are already there and I can extract them without rewriting.

This answer scores well because it shows you rejected something for a reason, not because you did not know it.

Q3What happens if two people book the same slot at the same time?

Sir, this is the main problem I designed for. I solved it in two layers.

On the server, I open a transaction and take a row lock on that stylist's bookings for that date, then re-check the slot. The lock makes the two requests happen one after another instead of together. The first one gets 201 Created. The second one finds the slot taken, rolls back, and gets 409 Conflict — and the customer is sent back to pick another time with a fresh list.

And in the database itself I have an exclusion constraint, so even a direct SQL insert of a clashing booking is refused. The lock gives a good error message; the constraint gives a guarantee.

Q4How are passwords stored?

Sir, I hash them with bcrypt at twelve rounds. I never store the plain password anywhere, and the hash is never returned in any API response.

Also, on a failed login I give a generic message — I do not say whether the email exists or the password was wrong. Otherwise someone could use the login page to find out which emails are registered.

Q5Explain how your login works. What is JWT?

Sir, JWT means JSON Web Token. When the user logs in, I verify the password and then create a token that contains his user ID and role, signed with a secret key on my server.

The frontend stores it and sends it with every request. My middleware verifies the signature — if anyone changes even one character, the signature fails. So the role inside the token cannot be edited by the user.

The access token expires in fifteen minutes, which limits the damage if it is stolen. For convenience I also issue a refresh token valid for seven days, kept in an httpOnly cookie so JavaScript cannot read it. I store it hashed on my server so I can revoke it on logout.

Q6Can one customer see another customer's booking?

No sir. Checking the role is not enough, because both users are customers. So on every record-level route I also check ownership — the booking's customer ID must match the user ID in the token.

And sir, one small detail — if he requests someone else's booking I return 404 Not Found, not 403 Forbidden. Because 403 would confirm that the booking exists, which is itself an information leak.

This small detail impresses examiners. It shows you thought past the obvious answer.

Q7How do you calculate the bill?

Sir, in a fixed order, and the order matters. First the subtotal from the line items. Then the coupon discount — if it is a percentage coupon it is capped at a maximum amount. Then the loyalty points discount. Then I apply GST on whatever amount remains. Then I subtract the advance already paid to get the balance due.

Sir, the order is important because if I applied GST before the discounts, the customer would pay tax on money he never actually paid. All of this is computed on the server — any amount coming from the browser is ignored completely.

Q8Why did you store the price again in booking_services? That is duplicate data.

Sir, it looks like duplication but it is about correctness. If today a haircut is three hundred rupees and next month the owner makes it four hundred, then an invoice that joins to the live table would also start showing four hundred. A past bill would silently change.

We have to keep invoices for seven years for tax purposes, so an old invoice must be exactly reproducible. That is why I take a snapshot of the price, name and duration at the time of booking. It is a deliberate decision and I have documented it so nobody "fixes" it later.

Q9Why a ledger for loyalty points? Why not just a balance column?

Sir, because points move in five different ways — earned, redeemed, expired, adjusted by the admin, and reversed on a refund. If I keep one balance number and any one of those operations fails halfway, that number becomes permanently wrong and I have no way to find the correct value.

With a ledger, every movement is a separate row and the balance is simply the sum. It can never drift, I can always recalculate, and the customer gets a full history for free. Sir, this is the same reason real accounting systems never store only a balance.

Q10Is your project scalable?

Sir, the main thing I designed for is that my API is stateless — I do not keep any session in the server's memory. Everything needed is in the token or the database. So I can run multiple copies of the API behind a load balancer without changing any code.

If it grows further, the next steps would be a Redis cache for data that rarely changes like services and settings, then a read replica so heavy reports do not slow down bookings, and then moving the cron jobs to a proper job queue.

But sir, right now it is sized for one salon with six stylists and about two hundred bookings a day, and one instance handles that comfortably. I did not want to add complexity for a scale that does not exist yet.

Q11What was the biggest challenge you faced?

Sir, the slot availability logic. It sounds simple but it has to combine four different things — the salon's hours, the stylist's individual shift and weekly off, his approved leave, and his existing bookings. And because services have different durations, I had to check range overlap, not just the start time.

And then on top of that, handling two customers booking at the same instant. That concurrency part took me the longest to understand and get right.

Never answer this with "CSS" or "deployment". Name a real logic problem — it shows where you actually did the thinking.

Q12Why only three roles? A receptionist is different from a stylist.

Sir, that is true, so I handled it as a type of staff rather than a fourth role. There is a staff_role field which can be stylist or receptionist.

The reason is that their permissions are almost identical — both take bookings and make bills. Adding a full fourth role would mean another column in every permission check for very little benefit. If the front desk later needs permissions a stylist must not have, then I will promote it to a proper role.

Q13What will you add in the future?

Sir, three things. First, multi-branch support, so one owner can manage several salons — that mainly means adding a branch reference to the tenant tables. Second, WhatsApp notifications instead of only email, because in India customers check WhatsApp more than email. Third, a proper automated test suite, which I have listed as a known gap.

Q14Did you write all of this yourself?

Answer this honestly and specifically. Say what you designed, what you wrote, what you took from documentation, and where you used AI assistance or tutorials. Then show that you understand it by explaining one hard part without notes.

Understanding your own code is what is actually being tested. A student who explains the slot algorithm clearly is in a far better position than one who claims everything and then cannot answer Q3.

Part 4

If something goes wrong

If this happensWhat to say and do
The page is very slow to load at first "Sir, this is the free hosting waking up — it sleeps after fifteen minutes. It takes about fifty seconds the first time. I have documented this as a known trade-off."
Then keep talking about the architecture while it loads. Do not stand in silence watching the screen.
A feature does not work "Sir, this part is not working at the moment. Let me show you the next one and I will check this after."
Say it once, calmly, and move on. Do not apologise three times — that draws more attention to it than the bug itself.
Sir asks something you do not know "Sir, I am not sure about that. I will check it and tell you."
This is a completely acceptable answer. Guessing wrongly is much worse, because the follow-up question will expose it.
Sir says a design choice is wrong Do not argue and do not immediately agree. "Sir, I chose it because [your reason]. But I understand your point — I will look at that approach."
Give your reason once, then accept the feedback gracefully.
You go blank Go back to the diagram and describe what you see layer by layer — purple, blue, green, orange. Describing a picture is much easier than recalling a speech, and it usually gets you moving again.
The internet fails completely This is why you keep the three documents and the diagrams saved or screenshotted on your laptop beforehand. Present from the diagrams and explain the flow. Do this preparation the night before, not on the day.

Checklist for the day

The night before

  • Say the Step 4 slot explanation out loud three times, without reading
  • Screenshot all three diagrams and save them on your laptop, in case the internet fails
  • Open all three document links once so they are in your browser history
  • Seed the demo data — a few past bookings so the dashboard charts are not empty
  • Test the two-window double-booking demo yourself, so you know it works
  • Note down your own answer to Q11 and Q14 in your own words

Two minutes before you present

  • Open the app so the backend wakes up — this is the one thing you must not forget
  • Have the architecture diagram open in a tab, ready to switch to
  • Have two browser windows ready for the double-booking demo
  • Log in as admin once, so the dashboard is already loaded

While speaking

  • Start with the problem, not the technology
  • Say why after every what
  • Speak slower than feels natural — nervousness makes everyone speed up
  • Pause after the question "What will happen?" in Step 4. The pause does real work
  • When you finish, ask: "Shall I show you the demo, sir?" — do not just stop
One last thing

You do not need to say everything on this page. A clear seven-minute explanation with three strong ideas beats a rushed fifteen-minute one that covers every table.

If you only get to say one thing, say the double-booking answer. That one is genuinely good engineering, and it is the part most student projects get wrong.
